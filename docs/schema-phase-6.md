# Schema, phase 6

Migration `db/migrations/0007_quick_marvel_zombies.sql` is generated by `drizzle-kit generate` from `db/schema.ts`. It has not been applied; the owner applies it with `npm run db:migrate`. No new tables, so no new row-level-security policies: the existing `user_settings` owner policy still applies. The Drizzle connection bypasses RLS, so every query still filters by the signed-in user's id.

## Changed table

`user_settings` gains one column:

- `auto_lock_minutes` (`integer`, null, default 5): minutes without activity before the app signs the person out. `null` means auto-lock is off. CHECK `user_settings_auto_lock_minutes_range`: null, or 1 to 120. Settings offers off, 1, 5, 15 and 30 (`AUTO_LOCK_CHOICES` in `db/schema.ts`).

The generated SQL:

```sql
ALTER TABLE "user_settings" ADD COLUMN "auto_lock_minutes" integer DEFAULT 5;
ALTER TABLE "user_settings" ADD CONSTRAINT "user_settings_auto_lock_minutes_range" CHECK (auto_lock_minutes is null or auto_lock_minutes between 1 and 120);
```

Because of the default, the existing settings row gets 5 on migrate, so auto-lock is on after the migration. Someone with no settings row yet also gets 5 (`getSettings`). The Settings page writes the column through `setAutoLock` (and `month_start_day` through `setMonthStartDay`) in `app/actions/settings.ts`.

## Not in the backup

The backup format is unchanged: `auto_lock_minutes` is a device preference and is not exported or restored (`lib/backup.ts` was not touched). A restored account starts at the default, 5 minutes.
