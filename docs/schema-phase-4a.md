# Schema, phase 4a

Migration `db/migrations/0003_polite_domino.sql` is generated by `drizzle-kit generate` from `db/schema.ts`. It has not been applied; the owner applies it with `npm run db:migrate`.

Every new table has `user_id -> auth.users (cascade)`, row-level security enabled and an `<table>_owner_all` policy (`user_id = auth.uid()`), like the earlier tables. The Drizzle connection bypasses RLS, so every query still filters by the signed-in user's id.

Scope: unit-based holdings only (`stock`, `fund`, `other`). Physical gold, Savings Clouds, loans and goal links to holdings are a later phase.

## New enums

`holding_kind` (`stock`, `fund`, `other`), `corporate_action_kind` (`BONUS`, `SPLIT`, `WRITE_OFF`).

## New tables

| Table | Columns and constraints |
|---|---|
| `holdings` | `account_id -> accounts` (the brokerage account), `kind`, `name`, `ticker` (null), `notes`, `archived_at`, `created_at`, `updated_at` |
| `price_updates` | `holding_id -> holdings (cascade)`, `date`, `price` (`numeric(20,6)`, >= 0), `created_at`. Index `(holding_id, date)` |
| `corporate_actions` | `holding_id -> holdings (cascade)`, `kind`, `date`, `quantity` (`numeric(20,6)`), `ratio` (`numeric(20,6)`), `note`, `created_at`. Index `(holding_id, date)` |

`corporate_actions` check: `BONUS` has `quantity > 0` and no `ratio`; `SPLIT` has `ratio > 0` and no `quantity`; `WRITE_OFF` has neither.

## Changed tables

- `transactions` gains `holding_id -> holdings` (null), `quantity` and `unit_price` (`numeric(20,6)`, null). Two checks:
  - `transactions_holding_type_check`: `holding_id` is only allowed on `INVESTMENT_PURCHASE`, `INVESTMENT_SALE` and `DIVIDEND`.
  - `transactions_quantity_price_check`: `quantity > 0` and `unit_price >= 0` are both set exactly for `INVESTMENT_PURCHASE` / `INVESTMENT_SALE` rows with a `holding_id`, and both null otherwise. Existing rows have no `holding_id`, so they pass.
- `user_settings` gains `stale_days_holdings` (integer, not null, default 7, check 1..365).

## Ledger rows

| Type | Account | `amount` (cash) | Other columns |
|---|---|---|---|
| `INVESTMENT_PURCHASE` | `from_account` = cash source | quantity x unit price + fee | `quantity`, `unit_price`, `fee`. The fee is added to cost basis, it is not spending |
| `INVESTMENT_SALE` | `to_account` = where cash lands | quantity x unit price - fee - tax withheld | `quantity`, `unit_price`, `fee`, `tax_withheld`, `gross_amount` = quantity x unit price |
| `DIVIDEND` | `to_account` | gross - tax withheld | `gross_amount`, `tax_withheld`; no quantity |

A bank to brokerage move stays a `TRANSFER` and is not investing. `transactions.realized_pl` stays unused.

## Model

- Quantity, cost basis, average cost, realized and unrealized P/L are never stored. They are replayed from a holding's dated events (purchases, sales, dividends, corporate actions) in order of date, then `created_at`. Cost basis method: average cost. Pending and void rows are ignored.
- A purchase, sale, corporate action, edit or void is refused if the replayed history would make the quantity negative on any date (`validateHistory`). That is enforced in application code, not by a database constraint.
- Corporate actions move no cash. `BONUS` adds quantity; `SPLIT` multiplies quantity by `ratio` (below 1 is a reverse split, rounded half up at the 6th decimal); both leave cost basis unchanged. `WRITE_OFF` zeroes quantity and basis, and the remaining basis is a realized loss. Rights issues are ordinary purchases.
- `price_updates` and `corporate_actions` are append-only. Value at a date uses the latest price on or before it (step function). With no price update a holding is valued at its last transaction price and marked as such. A value is stale when its latest price is more than `stale_days_holdings` days old.
- Expected returns stay in `financial_assumptions`; they are set by the user and shown as expected / assumed.

## Engine (`lib/finance-core`)

- `portfolio.ts`: `replayHolding`, `validateHistory`, `priceAsOf`, `holdingValue`, `lastTransactionPrice`, `staleness`, `portfolioValue`, `purchaseCash`, `saleCash`, `dividendCash`.
- `allocation.ts`: a percentage rule clipped by the pool now reports its unclipped share as `planned` and the cut as `shortfall`; `funded` is unchanged.
