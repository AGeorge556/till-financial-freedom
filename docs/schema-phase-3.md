# Schema, phase 3

Migration `db/migrations/0002_legal_energizer.sql` is generated by `drizzle-kit generate` from `db/schema.ts`. It has not been applied; the owner applies it with `npm run db:migrate`.

Every new table has `user_id -> auth.users (cascade)`, row-level security enabled and an `<table>_owner_all` policy (`user_id = auth.uid()`), like the phase 1 tables. The Drizzle connection bypasses RLS, so every query still filters by the signed-in user's id.

## New enums

`savings_target_mode` (`fixed`, `percentage`, `flexible`), `allocation_rule_kind` (`fixed`, `percentage`, `remainder`), `allocation_target_kind` (`goal`, `investments`, `cash`).

## New tables

| Table | Columns and constraints |
|---|---|
| `goals` | `name`, `target_amount` (> 0), `target_date`, `start_date`, `priority` (>= 1, 1 = highest), `planned_monthly` (null or >= 0), `expected_return_override` (`numeric(8,6)`, null), `manual_current` (null or >= 0), `notes`, `color`, `icon`, `archived_at`, `created_at`, `updated_at` |
| `goal_allocations` | `goal_id -> goals (cascade)`, `account_id -> accounts`, `amount` (> 0), `created_at`, `updated_at`. Unique `(goal_id, account_id)` |
| `goal_allocation_events` | `goal_id -> goals (cascade)`, `account_id -> accounts`, `delta` (signed, <> 0), `date` (Cairo date), `note`, `created_at`. Index `(user_id, date)` |
| `allocation_rules` | `kind`, `target_kind`, `goal_id -> goals (cascade)`, `amount`, `percent` (`numeric(8,6)`), `created_at` |
| `allocation_overrides` | `rule_id -> allocation_rules (cascade)`, `month` (`YYYY-MM`, start month of the financial month), `amount` (>= 0), `created_at`. Unique `(rule_id, month)` |

`allocation_rules` checks: `goal_id` is set exactly when `target_kind = 'goal'`; a `fixed` rule has `amount > 0` and no `percent`; a `percentage` rule has `0 < percent <= 1` and no `amount`; a `remainder` rule has neither. A partial unique index allows at most one `remainder` rule per user.

## Changed table

`user_settings` gains `savings_target_mode` (not null, default `flexible`), `savings_target_amount`, `savings_target_percent`, `expected_monthly_income`, `expected_monthly_spending` (all nullable). No other existing table changed.

## Model

- A goal is an earmark, not an account. Its current amount is the sum of its `goal_allocations`; with no allocations it uses `manual_current`.
- Allocations never create a transaction, so they never change an account balance or net worth. Each change to an allocation is recorded as a `goal_allocation_events` row (history is not overwritten); the actual monthly contribution is the net of the events dated in the financial month.
- The rule that an account's allocations stay within its balance is enforced in application code (`validateAllocationChange`), not by a database constraint.

## Engine (`lib/finance-core`)

- `allocation.ts`: `applyAllocationRules` (fixed by goal priority, then buckets, then percentage of what is left, then one remainder; monthly overrides act as fixed amounts for that month), `savingsTargetTotal`, `percentOf`.
- `goals.ts`: `goalCurrentAmount`, `accountFree`, `overAllocatedBy`, `validateAllocationChange`, `actualContribution`, `blendedReturn`, `plannedMonthly`, `goalProjection`, `trailingCapacity`.
