# Schema, phase 8 (edit everywhere)

Migration `db/migrations/0009_smiling_lord_hawal.sql` is generated by `drizzle-kit generate` from `db/schema.ts`. It has not been applied; the owner applies it with `npm run db:migrate`. It adds six nullable columns and nothing else.

## Rule

A correction never updates or deletes a financial row in place. The old row is marked void and, for an edit, a replacement row is inserted in the same database transaction. Ledger rows already had `status = 'void'` and `voided_at`; the six record tables below get `voided_at`. A voided row stays in the database and in the backup, is ignored by every calculation, and is hidden from normal lists.

## New columns

`voided_at timestamptz null` on:

| Table | What a voided row was |
|---|---|
| `price_updates` | a holding's price |
| `gold_prices` | a buy-back price per gram |
| `corporate_actions` | a bonus issue, split or write-off |
| `rate_history` | a Savings Cloud APY change |
| `cloud_confirmations` | a Savings Cloud confirmed value |
| `liability_updates` | a manual loan update |

Null means live. The "append-only" comments in `db/schema.ts` now say "corrected by voiding and replacing".

## Queries (`db/queries.ts`)

- Every reader that feeds a calculation or a normal list leaves voided rows out, through one helper, `visibleRows` (`lib/finance-core/voided.ts`): `listPriceUpdates`, `listGoldPrices`, `listCloudRecords`, `listLiabilityUpdates`, `loadPortfolio` (rates, confirmations and, through the others, prices, gold and corporate actions), `listHoldingEvents`, `holdingValueNow`, `loadWealth`, `loadMonth`, `loadNetWorthSnapshots`, `loadHistory` and the insight, reminder and scenario loaders that sit on them. Reads inside an action pass their transaction handle as before and get the same filtering, so a history check never sees a voided row.
- The backup readers still return voided rows: `listPriceUpdateRows`, `listCorporateActions` and `listWealthRows` (gold prices, rate history, confirmations, loan updates).
- `loadRemovedRecords(userId)` returns only the voided rows of the six tables, most recently removed first, for a "show removed" view. It never feeds a calculation.
- The entry types `HoldingPriceUpdate`, `GoldPriceEntry`, `RateHistoryEntry` and `CloudConfirmationEntry` now carry `voidedAt: string | null` (always null except from `loadRemovedRecords`). `CorporateActionRow` and `LiabilityUpdateRow` get the column from the table.

## Engine (`lib/finance-core`)

No existing behaviour changed. One validator per rule, each called on the whole proposed history:

| Rule | Validator |
|---|---|
| holding quantity never negative on any date | `validateHistory` (`portfolio.ts`) |
| cloud never over-withdrawn at any withdrawal date | `validateCloudHistory` (`clouds.ts`) |
| loan balance never below zero, in date order | `validateLiabilityHistory` (`liabilities.ts`) |
| account allocation within the balance | `validateAllocationChange` (`goals.ts`), unchanged |
| goal share of a holding at most 100% | `validateShareChange` (`goals.ts`), unchanged |
| editing an account's type, opening balance or investment flag | `validateAccountChange` (`ledger.ts`), new |

`validateAccountChange` refuses: a negative opening balance on anything but a credit card; holdings on an account that is not an investment account; and earmarks above the new balance. An account that was already over-allocated may still be edited as long as the edit does not make it worse.

## Not in the backup yet

`lib/backup.ts` and `app/actions/backup.ts` are not part of this step. Until they carry `voidedAt` for the six tables, an export drops it, so a restore would bring removed records back as live. Do this before applying the migration to real data: add `voidedAt` to the six backup shapes, parse and restore it, bump `BACKUP_VERSION`, and let version 6 files restore with it null.
