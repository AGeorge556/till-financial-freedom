# Schema, phase 4b

Migration `db/migrations/0004_blushing_sphinx.sql` is generated by `drizzle-kit generate` from `db/schema.ts`. It has not been applied; the owner applies it with `npm run db:migrate`.

Every new table has `user_id -> auth.users (cascade)`, row-level security enabled and an `<table>_owner_all` policy (`user_id = auth.uid()`), like the earlier tables. The Drizzle connection bypasses RLS, so every query still filters by the signed-in user's id.

Scope: physical gold, Savings Clouds, loans and money owed, and goal allocations funded by holdings. Bank certificates and other nominal paid-out products are not modelled.

## Migration caveat

`holding_kind` gains `gold` and `cloud` with `ALTER TYPE ... ADD VALUE`. Postgres 12+ allows that inside a transaction, but the new value cannot be used until the transaction commits, and `drizzle-kit migrate` runs every pending migration in one transaction. So no statement in the migration may mention `'gold'` or `'cloud'` as an enum literal. The two checks that need them compare `kind::text` instead. Do not "simplify" those checks back to `kind = 'gold'`, and do not add a data insert of the new kinds to this migration.

## New enums

`gold_form` (`bar`, `coin`, `jewelry`), `contribution_frequency` (`weekly`, `monthly`), `gold_price_mode` (`derive_24k`, `per_karat`), `liability_kind` (`loan`, `owed`, `other`). `holding_kind` is now `stock`, `fund`, `other`, `gold`, `cloud`.

| `rate_history` | `holding_id -> holdings (cascade)`, `effective_date`, `apy` (`numeric(8,6)`, > -1), `created_at`. Append-only. Index `(holding_id, effective_date)` |

| `liabilities` | `name`, `kind`, `opening_balance` (> 0), `interest_rate` (`numeric(8,6)`, null, >= 0, display only), `start_date`, `notes`, `archived_at`, `created_at`, `updated_at` |
| `liability_updates` | `liability_id -> liabilities (cascade)`, `date`, `delta` (bigint, <> 0, signed: positive owes more), `note`, `created_at`. Append-only. Index `(liability_id, date)` |

## Changed tables

- `holdings` gains `karat`, `form`, `start_date`, `maturity_date`, `contribution_amount` (bigint piasters) and `contribution_frequency`, all null. Checks: `karat` (24, 21 or 18) and `form` are set exactly when `kind = 'gold'`; the four cloud fields are only allowed when `kind = 'cloud'`; `maturity_date >= start_date` when both are set; `contribution_amount` and `contribution_frequency` are both set or both null, and the amount is > 0. A cloud is not required to have a `start_date` in the database; the form should ask for it. Existing rows are `stock`, `fund` or `other` with all of these null, so they pass.
- `transactions` gains `liability_id -> liabilities` (null), allowed only on `LIABILITY_PAYMENT` and `EXPENSE` rows. `transactions_quantity_price_check` is relaxed: an `INVESTMENT_PURCHASE` / `INVESTMENT_SALE` row with a `holding_id` has `quantity > 0` and `unit_price >= 0` both set (unit-based holdings and gold) or both null (cloud deposits and withdrawals); every other row has both null. Whether a holding needs both or neither depends on its kind, which a row-local check cannot see, so the server action enforces that. Existing rows keep passing.
- `goal_allocations`: `account_id` and `amount` become nullable; `holding_id -> holdings` and `percent` (`numeric(8,6)`) are added. `goal_allocations_shape_check` replaces `goal_allocations_amount_check`: exactly one shape, either `account_id` with `amount > 0` (and no holding or percent), or `holding_id` with `0 < percent <= 1` (and no account or amount). New unique `(goal_id, holding_id)`. That the shares on one holding sum to at most 100% across goals is enforced in application code (`validateShareChange`, with the row locked), not by a constraint.
- `goal_allocation_events`: `account_id` becomes nullable; `holding_id` and `percent_delta` (`numeric(8,6)`, signed) are added. `delta` stays the EGP value of the change at that moment. A check requires either an account (no holding, no percent delta) or a holding with a non-zero percent delta.
- `user_settings` gains `gold_price_mode` (`derive_24k` by default), `stale_days_gold` (default 14) and `stale_days_clouds` (default 30), both checked 1..365.

## Ledger rows

| Case | Type | Columns |
|---|---|---|
| Gold purchase | `INVESTMENT_PURCHASE` | `quantity` = grams, `unit_price` = metal price per gram for the karat, `fee` = workmanship (goes into cost basis). `amount` = grams x price + workmanship |
| Gold sale | `INVESTMENT_SALE` | like any holding sale |
| Cloud deposit / withdrawal | `INVESTMENT_PURCHASE` / `INVESTMENT_SALE` | `holding_id`, no `quantity`, no `unit_price`; `amount` is the cash |
| Loan payment | `LIABILITY_PAYMENT` + (if interest > 0) `EXPENSE` | one action, one transaction. The payment row is the principal and carries `liability_id`. The expense row is the interest, in a category the user picks, and carries `liability_id` |

Depositing into a cloud is investing, not spending. Principal is not spending; interest is.

## Model

- Gold is valued at the buy-back price per gram (`gold_prices`), never the purchase price. `derive_24k` mode uses only the 24K rows and derives the other karats as price x karat / 24 in fixed-point; `per_karat` mode uses each karat's own rows. Value as of a date uses the latest price on or before it, never interpolated. With no price the holding is valued at its last transaction price and marked as such. Stale after `stale_days_gold`.
- Cloud value is an estimate: the latest confirmed value (the anchor), plus the deposits and withdrawals dated after it, each growing from its own date by `(1 + apy)^(days / 365)` across the APY changes in `rate_history`. Before the first recorded rate there is no growth. A confirmation becomes the new anchor. The label is `confirmed` only on the anchor date with nothing after it, otherwise `estimated`. Cost basis = deposits - withdrawals, never negative; growth = value - basis and is market change, not income. A withdrawal above the estimated value is refused. Stale after `stale_days_clouds` since the latest confirmation.
- Outstanding balance of a liability = opening + sum of `liability_updates` - sum of posted principal payments, never negative. Net worth = cash + holdings (stock/fund, gold, clouds) - liabilities. In the reconciliation identity a liability update is an adjustment (negative for net worth when it adds debt) and a principal payment leaves net worth unchanged.
- A holding allocation's value is `percent x` the holding's current value, so it moves with the market. Changing a share moves no money; its event records the percent delta and the EGP value of that delta at that moment, so later growth is never counted as a contribution. A goal's expected return is the value-weighted average of its sources' assumed returns (cash `cash_return`, stock/fund/other `stock_return`, gold `gold_return`, cloud its current APY, unset = 0) unless the goal has its own override.

## Engine (`lib/finance-core`)

- `gold.ts`: `karatPrice`, `goldPricesFor`, `goldPriceAsOf`, `goldValue`, `goldPurchaseEvent`.
- `clouds.ts`: `growthFactor`, `apyAsOf`, `cloudEstimate`, `validateWithdrawal`, `validateCloudHistory`, `cloudProjection`, `cloudStaleness`, `cloudLine`.
- `liabilities.ts`: `outstanding`, `validatePayment`, `totalLiabilities`, `liabilityAdjustments`.
- `goals.ts`: `AllocationSource`, `goalCurrentAmount` (now takes sources, not bare amounts), `shareValue`, `holdingFreeShare`, `validateShareChange`, `shareChangeEvent`, `sourceReturn`, `attributeOverAllocation`.
- `portfolio.ts`: `portfolioValue` takes an optional per-holding `staleDays` and optional cloud lines, so gold and clouds are in the total. A reverse split that rounds the quantity to 0 while cost basis remains is refused (record a write-off instead), and a sale's net proceeds must be positive, the same rule as `saleCash`.
